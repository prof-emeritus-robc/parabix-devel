# Plan: masked NFC, with the NFC generator rewritten in C++

Status (2026-11-19): plan. Part of step 6 of `doc/masked-transforms-plan.md`
(normalization with a mask). Masked NFD and NFKD are done in Unicode mode
(`NFD_U21_Pipeline` with a mask, commit ff6c907b2). NFC, NFKC and FCC still use
barrier substitution (`RulePipelineBuilder::barrierNormalization`,
`UTF8PipelineBuilder::maskedNormalization`).

## Goal

NFC of a text with a mask, where each run of the mask is normalized by itself.
Characters outside the mask stay unchanged, and nothing composes or reorders
across them. This is what barrier substitution computes today. The aims:

- **No barrier substitution.** No replacement of the outside characters, no
  barrier classes, and no FilterByMask/SpreadByMask restoration.
- **One kernel set.** The kernel code must not depend on the mask's contents,
  so every filter shares the same kernels.
- **Native in UTF-8 mode.** NFC is byte-based already, so a UTF-8-mode
  transform (95 of the 112 CLDR transforms with masked normalization run in
  UTF-8 mode) needs no conversion to or from 21-bit code points.
- **An output mask.** The output must report which positions are within the
  mask, so tconv can keep its masks in step (`PositionMap`).

In CLDR, NFC under a global filter occurs 126 times, NFKC twice, and FCC is
built on NFC passes. Every `--lines` run that normalizes also goes through
this path.

## The NFC pipeline today

`NFC_FocusedTransform` (`lib/kernel/unicode/normalization/nfc.cpp`) runs these
stages:

1. **Focus.** `NFC_CandidateClass` and `NFC_Focus` select the composable second
   characters, the character before each, and the excluded composites, as
   whole UTF-8 characters (`U8Spans`).
2. **Filter.** The work regions are extracted into a focused byte stream. The
   regions are concatenated, so characters from different regions become
   adjacent.
3. **Transform.** `NFC_Transform`:
   - `NFC_Initial_Insertion`, then `InsertionSpreadMask` and `SpreadByMask` to
     make room;
   - `NFC_WorkingSpaceTransform`:
     - `ExcludedCompositeStage` and `SingletonCanonicalization`;
     - ccc = NR (`ccc_NR`);
     - `ShortComposablePipeline`: 5 passes of `ShortComposableTranslationN` and
       `SelfComposableTranslation`;
     - `LongComposablePipeline`: 6 passes of `FindComposablesN`,
       `IndexedShiftBack` and `ApplyLongCompositionN`, with pass 3 run twice;
     - `Hangul_Composables` and `Hangul_Composition`;
     - `ValidWorkMask` and compression;
     - decoding to 21-bit code points, sorting runs of nonzero ccc, and
       re-encoding to UTF-8.
4. **Placement and reintegration.** The transformed bytes are merged with the
   unchanged source bytes.

Most of the kernels are generated by `scripts/UCD/nfc_generator.py` (about
2,000 lines of Python) into `normalization-generated.cpp` (17,705 lines,
including 2,580 UnicodeSet tables). The generator does two jobs:

- **Analysis**, from the UCD:
  - `create_mappings`: singletons, excluded composites, and short, long and
    self composables;
  - `add_overridable_seconds` and `determine_overridable_primaries`
    (A BC → AB C);
  - `create_max_insert_map`;
  - `allocate_ccc_passes`: separate passes, so a starter composes with its
    lowest-ccc mark first;
  - `allocate_chained_short_passes`: dependence order, and the self-composable
    pass;
  - `create_conditional_mark_codes`.
- **Emission.** For each kernel, prefix-based scopes (an `If` on the UTF-8 lead
  byte range), `UTF::UTF_Compiler::compile(vars, usets)` for the classes of
  that range, then case logic built from templates.

## What a mask must do, stage by stage

The mask is a byte stream with a 1 on every byte of each character inside the
mask, as `UTF8_CharSpans` already produces in UTF-8 mode.

| Stage | Condition with a mask |
|---|---|
| Insertion (`NFC_Initial_Insertion`) | no room is made for characters outside the mask (insertion classes ∧ mask) |
| Singletons, excluded composites | per character: classes ∧ mask |
| Short and self composables, Hangul L V T | pairs of adjacent characters: both classes ∧ mask (adjacent characters in the mask are in the same run) |
| Long composition (`FindComposablesN`) | starter and mark classes ∧ mask, and a character outside the mask blocks the scan: the `ccc_NR` input becomes `ccc_NR ∨ outside`, so `AdvanceThenScanTo` stops there, and `IndexedShiftBack` cannot shift a mark code past it |
| Overridable primaries | as long composition (they are long composables) |
| Canonical ordering (sort) | after composition, a ccc of 0 starts a new run; a character outside the mask is also a run boundary (see Canonical ordering below) |
| Focus | candidates ∧ mask and excluded composites ∧ mask; the character before a candidate is kept even when it is outside the mask (see below) |

In every kernel the change is the same: each class stream is ANDed with the
mask at the class's position. With `BitMovementMode::LookAhead` the class
marks a character's first byte, and the mask covers every byte, so one AND per
class is enough. Long composition also needs one OR into its blocking set.

### Canonical ordering

The working space composes first and sorts after. Sorting first would not make
a starter and its partner adjacent: a mark of a lower combining class may still
come between them, so long composition must find the partner past such marks
anyway (`AdvanceThenScanTo` over the classes of its pass). After composition,
the sort relies only on runs of nonzero ccc, and a character of ccc 0 always
starts a new run.

NFC's own focus includes every character of nonzero ccc, so without an
external mask no run is split by the focus. With an externally defined mask,
a character outside it can still be a nonstarter in the working space: a
predecessor kept for the focus seam (below). In `q U+0301 [U+0323] U+0302`,
where only U+0323 is outside the mask, the run U+0301 U+0323 U+0302 would be
sorted across it, while barrier substitution makes U+0323 a starter. Such
regions are unlikely to have practical uses, but the result must still match:
the positions outside the mask are run boundaries for the sort (the runs are
nonzero ccc ∧ mask), at the cost of one AND.

The sort can work on the UTF-8 bytes directly, instead of decoding to 21-bit
code points (`UTF8_Decoder`, `UTF8_index`, FilterByMask) and encoding back
(`U21_to_UTF8`). The ccc of each character is spread to all of its bytes, and
the runs are sorted by it with the stable sort. The bytes of one character
have equal keys, so they stay together and in order, and characters of equal
ccc keep their order. The mask is then already in byte space for the run
boundaries and the output mask. The masked byte-level NFD (UTF-8 mode) can
use the same sort.

`SortRuns` sorts runs of up to 2^parallelSteps items with the odd-even merge
network (`OddEvenMergeSortRuns`, k(k + 1)/2 comparison steps for 2^k items).
Longer runs are completed by `SeqSortRuns`, which passes sorted runs through
unchanged. The default, `--parallel-sort-steps=2` (runs of up to 4 items), was
chosen for characters. In bytes a mark takes 2 or 3 bytes, so a run of two
marks already exceeds 4 positions and would fall through to the sequential
sort. The byte sort therefore needs its own number of steps, passed to
`SortRuns` explicitly rather than taken from the option shared with the
21-bit sorts:
- 3 steps: 6 comparison steps, runs of up to 8 bytes, typically 3 or 4 marks;
- 4 steps: 10 comparison steps, runs of up to 16 bytes.

Choose by the distribution of run lengths in bytes on mark-heavy text
(Vietnamese, polytonic Greek, Hebrew and Arabic with points, Indic scripts),
measured against the cost of each step and of the sequential sort. The
comparisons also carry 8 data bits per position instead of 21.

The distribution must be taken after composition. In NFC the sort follows the
compositions, which absorb most marks into their starters (e.g. Vietnamese and
polytonic Greek usually compose completely), so the remaining runs are
generally shorter than NFD's, where every mark stays in the run. NFC may
therefore need fewer steps than a byte sort for NFD, and the two choices are
made separately.

### The focus seam

The transform runs on concatenated work regions. Today no composition crosses
a seam because a region never begins with a composable second. A region
begins with the character before its first candidate, and if that character
were itself a candidate, its own predecessor would be in the focus and the
regions would merge.

With a mask, a candidate at the start of a run has its predecessor outside the
mask. If that predecessor were dropped from the focus, the region would begin
with a composable second, which could compose with the end of the previous
region across the seam. The fix is to keep the predecessor in the region even
though it is outside the mask. In the focused stream it acts as an inert
separator: its mask bits are 0, so no class matches it and it blocks long
composition. It is copied to the output unchanged, and reintegration writes
back the same bytes.

### Carrying the mask, and the output mask

The mask has to travel with the bytes through the pipeline:

1. **Focus and filter:** the focused mask is FilterByMask of the source mask by
   the work mask, alongside the bytes.
2. **Working space:** the mask is spread with the insertion spread mask, and
   inserted bytes inherit the mask of the character they follow. The
   compression filters it by `ValidWorkMask`.
3. **Sort:** on the bytes (see Canonical ordering): the mask gives the run
   boundaries and is not permuted, since nothing moves across it.
4. **Placement and reintegration:** the output mask merges the source mask (for
   the unmodified bytes) with the transformed mask (for the placed bytes),
   using the same placement as the bytes.

`FocusedTransform` needs an auxiliary-stream facility for this: streams
filtered, transformed and reintegrated together with the basis. That facility
would serve any masked focused transform, including UTF-8-mode NFD later.

tconv then has a position map in Unicode mode, `remove(selected)` followed by
`insert(outputMask, In)`, the same map barrier normalization uses. In UTF-8
mode the output byte mask replaces the masks directly.

### Focused or in place

There are two ways to apply masked NFC, and both are kept:

- **Focused.** Filter the work regions into a short stream, transform it, then
  spread and reintegrate the result, as `NFC_FocusedTransform` does today, with
  the masked focus, the seam separators and the auxiliary mask stream above.
- **In place.** Run the same kernels over the whole text under the mask, with
  no filter or spread of the work regions. The mask alone keeps the work to its
  runs. There are no seams, because nothing is concatenated, and the output
  mask is the working space's mask after compression.

Which is cheaper depends on how much work each byte or character costs in the
transform, against the cost of filtering and spreading it, and on how dense the
work is. A sparse focus over an expensive transform favours filtering. Dense
work, or a cheap transform, favours working in place. Filter and spread are
themselves an area for improvement in the pipeline, which will shift the
balance, so both paths stay available: the same kernel set (the mask is an
input), with the choice made by `FocusOptions::Focus` today and possibly
estimated later. This holds for every masked transform, not only NFC (see
doc/masked-transforms-plan.md, Execution).

## A U21 mode of NFC

tconv's Unicode mode (and any application working on the 21-bit basis)
currently pays a conversion to UTF-8 and back around NFC (`UTF8_Of`,
`BasisOf`, `U21_Of`). NFC should also run on the 21-bit basis directly. The
analysis (`NFC_Tables`) does not depend on the encoding, only the kernels do:

- **Classes:** compiled on the 21-bit basis, with one position per character,
  and scopes by code point range (high bits) in place of the UTF-8 lead-byte
  scopes.
- **Adjacency:** the offset between a character and the next is always 1,
  where the UTF-8 kernels advance by the length of the first character.
- **Insertions and deletions:** counted in characters. An excluded composite
  expands by its decomposition's length minus 1, and a composition deletes one
  position.
- **Hangul composition:** by arithmetic on the code points, as `LVT2NFD` does
  for decomposition.
- **Canonical ordering:** `SortRuns` on the 21-bit basis, as now inside the
  working space but without the decoding, with its own number of parallel steps
  (see Canonical ordering).
- **Focus:** candidates by character, and the same seam rule.

The C++ rewrite makes the encoding a parameter of the kernel classes (UTF-8 or
U21), which is a further reason for it: the generated templates are written for
UTF-8 bytes throughout.

## Rewriting the generator in C++

The analysis would move into a C++ class computed once at run time from the
UCD property objects tconv already uses: `dm`, `dt`, `Comp_Ex`/CE and `ccc`.
The emission would become ordinary kernel classes whose `generatePabloMethod`
builds the same Pablo code from those tables.

**For:**

- **One switch for the mask.** It touches every generated kernel. In C++ it is
  one constructor parameter per kernel class, instead of changes to a dozen
  string templates and a regenerated 17,705-line file.
- **Reviewable code.** The generated file is hard to review, and the passes and
  conditional codes are visible only as their output. In C++ they become data
  that `--plan`-style dumps and tests can inspect.
- **One code base.** Unicode updates go through the same UCD tables as
  everything else. There is no second Python data path, and no regeneration
  step to forget (see commit 0a528d0dc, a silently broken generated stage).
- **Room for NFKC.** The same analysis can be parameterized later, e.g. for a
  fused NFKC.

**Against:**

- **Size.** About 2,000 lines of Python logic to port faithfully, including the
  subtle passes: chained short passes, overridable primaries and conditional
  mark codes.
- **Start-up.** The tables are computed at run time. Each kernel already
  builds its Pablo code at run time, so only the analysis is new, and it is
  small: a few thousand decompositions. Measure it.
- **Cache names.** Generated names such as `FindComposables0_8x1` are fixed;
  runtime-built kernels need names that capture their tables. Once the port is
  stable, the names include the Unicode version (`UCD::UnicodeVersion`,
  `include/ucd/core/UCD_Config.h`), which determines the tables, plus a mask
  suffix. While the analysis is still changing, a hash of its results serves
  instead, so that a change in the analysis cannot reuse stale objects.

### Structure

- `NFC_Tables`: the analysis, one-to-one with the generator's methods, built
  once (a static accessor, as `caseMapData` is in tconv). Its fields are the
  maps the generator builds: `singleton_map`, `excluded_composite_map`,
  `short_composable_map`, `long_composable_map`, `self_composables`,
  `overridable_primaries`, `max_insert_map`, `ccc_pass_allocation`,
  `short_pass_map` and `conditional_mark_codes`.
- A helper for the prefix scopes: for a set of code points grouped by
  prefix-based range (`range_usets_from_cps`), open an `If` on the lead-byte
  test, compile the scope's classes with `UTF::UTF_Compiler`, AND them with the
  mask when there is one, and hand them to the case logic. This replaces
  `Uset_Builder`.
- Kernel classes:
  - `NFC_InsertionKernel`
  - `SingletonStage`
  - `ExcludedCompositeStage`
  - `SelfComposableStage`
  - `ShortComposableStage(pass)`
  - `FindComposables(pass)`
  - `ApplyLongComposition(pass)`
  - `NFC_CandidateClass`

  Each takes an optional `Mask` input binding, with the same lookahead as
  `Basis`.
- Pipeline functions, as today: `ShortComposablePipeline`,
  `LongComposablePipeline` and `NFC_WorkingSpaceTransform`, with the mask
  threaded through, and the encoding (UTF-8 or U21, see A U21 mode of NFC) a
  parameter of each kernel class.

### Repeated applications of a pass

The generator runs long-composition pass 3 twice
(`generate_long_composable_pipeline` special-cases `pass_no == 3`). Some
compositions take two steps with marks of combining class A (230, above):
a starter composes with a first mark of class A, and the composite then
composes with a second mark of the same class. A single application of the
pass finds only the first mark for each starter.

The C++ analysis derives this instead of hard-coding it. For each pass (a set
of combining classes), the number of applications is the length of the longest
chain of compositions through it: starter + mark₁ → p₁, p₁ + mark₂ → p₂, and
so on, with each mark of a class in the pass. Today that gives two for pass 3
and one elsewhere. A later Unicode version with more marks of one class in such
chains would then be handled, though this seems unlikely.

The second application need not repeat the whole pass. Two ways to do it:

- **A reduced application.** Look only for the second marks: those that
  compose with a composite of the pass, starting from those composites. Its
  classes and cases are a small subset of the pass's.
- **Folded into the pass.** Find the second mark in the same kernel, after the
  first (the composite's next unblocked mark of the class), and apply both
  compositions at once.

The reduced application is the simpler port, and it keeps a kernel for each
step. Folding saves a FindComposables/IndexedShiftBack/ApplyLongComposition
round, but needs the two marks' positions together. Choose after the port
(step 2), by kernel counts and run time.

     The same holds for U+1EED, U+1EE0, U+1EEC and U+1EDE with U+0328.
   - **A short composition matched on the second character's trailing bytes.**
     `U+0B47 U+1B3E` composes to U+1B4B, as `U+0B47 U+0B3E` composes to U+0B4B.
     U+1B3E is `E1 AC BE`, and U+0B3E is `E0 AC BE`. The class of the second
     character, compiled with an extra lookahead in the scope of the first's
     prefix, apparently does not test its lead byte.
   - **Focused reintegration after a wrong output length.** Where the first
     error changes the output's length, the focused transform misplaces
     everything after it: 1,262 of 1,900 lines of the pairs test differ from
     the reference, where the unfocused transform has 3.

   Fixed (2026-11-19):
   - **Short composition, second character's lead byte.** The cause was in
     `UTF::UTF_Compiler`: with an extra lookahead, `U8_Lookahead_Compiler`
     looked the suffix bytes ahead (by the extra lookahead + k) but tested the
     first code unit at the position itself. It now looks the first code unit
     ahead too (`adjustBasis`). This fixes the generated kernels as well.
   - **Overridable primaries.** `NFC_Tables` now derives them from a reference
     NFC (UAX #15 on the UCD's decompositions, classes and exclusions), rather
     than constructing them one level deep as the generator does. For each
     starter P in NFC whose decomposition has marks, and each composing mark m
     of a lower class than one of them, NFC(P m) is recorded where it is
     neither P m nor the composite of P and m. This reproduces the generator's
     938 entries and adds 320, e.g. U+1EE1 U+0328 → U+01EB U+031B U+0303.
     An override now writes its starter, then zeroes, then the marks that
     remain, right-aligned in P's region (`compositionTarget`). P's insertion
     room covers the longest composite its starter may still become, plus
     those marks (`maxReach`; 309 insertion amounts change). Before, the marks
     followed the starter directly, and a later composition, as of Ơ with
     U+0323 to Ợ, overwrote them. These fixes are in the C++ kernels only; the
     generated kernels, to be retired, keep the error. The analysis's dump
     therefore no longer equals the generator's in these entries.
   - **Focused reintegration** was a consequence of the overridable primaries'
     invalid UTF-8. The decoding, sort and encoding of the working space turned
     it into U+FFFD, a length the placement did not expect. Valid input no
     longer produces it. The byte sort would remove that decoding as well.

   With the fixes, every test input above (every code point, the compositions,
   the random sequences and NormalizationTest.txt) gives the reference NFC,
   focused and unfocused. `QA/nfc/TestFiles/composition_regressions` (in
   `normalization_test`) has the cases.

5. **U21 mode.** Kernel classes on the 21-bit basis (see A U21 mode of NFC),
   unmasked then masked, checked against the UTF-8 kernels by the same tests,
   and measured against the conversion to UTF-8 and back.

   Done (2026-11-19), in place. `NFC_U21(P, U21, Mask, OutputMask)`
   (`nfc_kernels.cpp`) runs on the 21-bit basis, one position per character.
   - **Room:** the positions inserted are for an excluded composite's
     decomposition and the marks an override leaves. A composite never needs
     room, so there is no `maxReach` here.
   - **Character stages** (`CharacterStage21`): a replacement's first
     character XORed in place, the others written into the inserted positions.
   - **Short and self composables** (`ShortComposableStage21`,
     `SelfComposableStage21`): the second character is a class compiled with
     `Parabix_CC_Compiler_Builder` on the basis looked ahead by 1, and
     `SelfComposableLogic` is given no UTF-8 suffixes.
   - **Long compositions** (`FindComposablesStage21`,
     `ApplyLongCompositionStage21`): as in UTF-8 mode, by the same pass data
     and mark codes. An override writes its starter in place and its marks
     after it.
   - **Hangul:** the existing kernels, on the 21-bit basis.
   - **Sort:** `SortRuns` on the compressed result, with no decoding.
   - **Mask:** as in step 3.

   `nfc -nfc-u21` decodes, normalizes and encodes, and `-nfc-u21-via-utf8`

   decode) for comparison. Every input (the pairs, random text, every code

   -segment-size=1`, every input gives the masked reference.

   |---|---|---|---|

   Where the work is dense, U21 in place wins, by avoiding the conversions.
   Where it is sparse, the focused route through UTF-8 wins despite them. A

   Focused U21 (2026-11-19): `NFC_U21(…, focus)`, focused by default, `nfc

     character).
   - **Transform:** the work is filtered by character (the mask with it), and
     `U21_Transform` (the in-place transform, which also gives the valid

   - **Placement:** as `NFC_WorkPlacement`: the source expanded by the same
     insertions at the work (∧ the mask), the working space's valid positions

     characters, and likewise the output mask.

6. **tconv.**

     output mask, replacing `barrierNormalization` for NFC and NFKC (masked

   - FCC: its passes call NFC with a selection, which is the same interface.

     transform with NFC, NFKC or FCC under a filter, also with `--lines` and
     with multiple threads, then measure.

   Done (2026-11-19), `--u21-nfc` (default on).
   - **Unicode mode**:
     - NFC, NFKC and FCC compose with `NFC_U21`, unmasked as well, with no
       conversion through UTF-8.
     - Within a filter (`maskedNormalization`), NFC is `maskedNFC`: the
       position map deletes the selected characters and inserts the composed
       ones (the output mask) within the masks, as barrier normalization did.
     - NFKC is the masked NFKD, then the masked NFC of the selection mapped
       through it.
     - FCC (`fcc(U21, mask)`) is the masked NFD, then each pass's masked NFC
       of the window within the mask, the mask mapped through each pass.
   - **UTF-8 mode**: NFC within a filter is `NFC_Masked` of the bytes
     (focused), with the output byte mask for the position map. NFKC and NFD
     keep barrier substitution in UTF-8 mode (there is no masked UTF-8 NFKD).

   Two more errors were found and fixed:

## Open questions

- **The byte sort's cost.** Runs are longer in bytes than in characters (2 to
  4 bytes per mark). Measure the byte sort, with its number of parallel steps
  (see Canonical ordering), against the decode, sort and encode it replaces,
  in the working space and on mark-heavy text.
- **UTF-8 mode NFD.** The same auxiliary-stream focus would give a masked
  focused NFD in UTF-8 mode, which is the other remaining part of step 6.
- **Lookahead of the mask binding.** Each kernel's `Basis` lookahead (up to 7
  for short composables) applies to the mask as well, because classes compiled
  in `LookAhead` mode test it at the same offsets.
