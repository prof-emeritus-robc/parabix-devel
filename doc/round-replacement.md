Survey of branch LDML at `d3d0aadc1` (2026-11-17); status re-surveyed at `d7854835d` (2026-11-19), see the next section. DivCode now resolves before contexts matched against the converted text with a monotone Pablo `While` loop (doc/ldml-divcode-plan.md §10–§12). ## 1. Correction kernel with unrolled rounds

`FusedRules` with `rounds > 0` applies the rules whose before contexts the group's conversions can change. Round 0 matches them against the text; each further round rebuilds the converted text from all results so far (lengths, characters, inserted texts), recomputes the converted characters before each position, matches the contexts again, and drops matches starting inside matches applied in the previous round (`settle`). All 9 copies run in every block.

Why it has not been a While loop: each round recomputes from scratch and drops matches, so it is not monotone, and in a carry-collapsing While an `Advance` reads the previous block's carry only in the first iteration. doc/ldml-xlit-coverage.md §3.1 still says While loops cannot be used. DivCode §10 shows they can, if the state only accumulates (known-in / known-out streams, `K1 |= MatchStar(next(In) ∨ K1, Del)`), with a frontier of newly decided positions. The same reformulation applies here: a before context depends only on positions to its left, so a three-valued state decided left to right converges, with as many iterations as the longest dependency chain, and none in blocks without a frontier.

Expected gains: exact at any chain length (the W4 fuzzing found rule sets needing 32 rounds), one copy of the body instead of nine (compile time and kernel size, see the table), and run time spent only where chains exist (DivCode's InterIndic-Latin went from +62% to −27% when its rounds were replaced).

### 1A. String-rule overlaps, two-way or self (whole-group correction: the selection of the string matches is redone in every round)

The selection is a left-to-right fixpoint of the same kind as the converted contexts: a match applies if its context holds and it does not start within an applied match. Kept as three-valued state (known applied, known rejected), each While iteration decides the matches whose earlier overlapping candidates are decided. Hans-Hant, Latin-InterIndic, Latn-Ethi/SERA and und_FONIPA-ar exceeded `--whole-group-rules` (256), so the before contexts of their string rules were matched against the unconverted text (the `--plan` warnings). Since 2026-11-22 the default is 512, which takes in und_FONIPA-ar (440 string rules; cold compile 69 s) and Latn-Kana and Latn-Hira (325; 23 s and 45 s), making them identical to ICU4C on their comparison inputs (Latn-Kana and Latn-Hira differed on 8 lines: `ahy` gave `アブ`, the earlier `h → ー` and the later `hy → ヒ` both applied). Where a group is still not applied in one kernel (Hans-Hant, Latin-InterIndic, Latn-Ethi/SERA over the limit; it-am and it-ja, whose subgroups yield to earlier rules; Latn-Grek/UNGEGN and Zawgyi-my, with MultipleCaptureMultipleReplacement rules selected with the string rules), xlit now also warns on the standard error when it applies the group, with the first such rule and the reason. That limit guards against nine copies of the whole group; with one copy of the body in a loop it could be raised, making these groups exact as well.

**Chunked staged rounds (2026-11-22).** A group with more string rules than `--staged-chunk-rules` (256), whose string matches are selected sequentially in staged rounds, is now applied in chunks. Only the string rules whose before contexts are matched against the converted text (the core) are in the kernels of each round. The others are matched once, in chunks, into per-length start streams; in each round they are applied in chunks where `LeftmostMatches` selects them, and their results are ORed with those of the core and subgroup kernel (`MergeFusedResults`), with the subgroups applied outside the static matches. Such a group needs only its core within `--whole-group-rules`. This takes in Latin-InterIndic (31 of 2,388 string rules in the core), Hans-Hant (10 of 958) and Latn-Ethi/SERA (8 of 531), with no warnings. On their comparison inputs, xlit and ICU4C now agree on Latin-InterIndic and Hans-Hant (0 of 501 lines each); Latn-Ethi/SERA still differs on the 2 lines where ICU4C ignores the filter (ICU4J agrees with xlit). On 1,000 random Latin words, Latin-InterIndic and Latn-Ethi/SERA agree with ICU4C (`xi` now gives `क्सि`, `hao` `हॊ` in Latn-Deva). Cold compiles: Latin-InterIndic 15 s, Hans-Hant 37 s, Latn-Ethi/SERA 4 s (whole transforms). With `--sequential-while=0`, the chunked and unchunked rounds give identical output on Any-Publishing, es_FONIPA-zh, ro-ro_FONIPA, zh_Latn_PINYIN-ru, ta-ta_FONIPA and und_FONIPA-fa. `QA/xlit_staged_chunks_test.py`. A group that the While loop resolves and that fits `--whole-group-rules` still takes the While loop; und_FONIPA-ar (383 of its 440 string rules in the core) gains nothing from the chunking.

**Fixed: wrong characters in Hans-Hant (2026-11-23).** The chunked rounds converted single characters to wrong ones (给 → 獷, ICU 給; 维, 终 → 獷; 鲁 → 鈽) on 5 of the first 5,846 lines of `nat-zh`, deterministically, depending on the position: 给 after a line of exactly 17 characters. The core kernel of Hans-Hant reads its 428 classes as a 12-bit code computed on the bytes (the hybrid groups), and that code was wrong for a character whose last byte began a 128-byte block. The UTF-8 class compiler, in `Advance` mode (classes marked at the last byte), nested an If on a second-byte test (BB of 给, E7 BB 99) whose body works at the third byte; another class needing the same `Advance` of that test outside the If, the body had no carry of its own, and was skipped in the block where the third byte is. Its If now tests the test moved to the next code unit (`lib/ucd/utf/utf_compiler.cpp`); `tests/utf8_classes_test.py` checks classes on the UTF-8 bytes against a reference at every offset from the block boundaries. Unrelated to the chunking: the unchunked kernel's 1,097 classes are not coded, and the fallback only escaped it. Also fixed on the way: `CharClassesKernel`'s signature lacked the bit movement and the mask, so a pipeline cached in one mode was reused for the other.

**Groups split by their independent components (2026-11-23).** A conversion group of more than `--split-components` rules (512; 0: none) is split by its independent components (`ldml::IndependentComponents`): the components with rules that have before contexts, then the others, as two groups separated by `:: Null ;` (`ldml::SplitIndependentComponents`). Applying independent components one after the other gives what the group gives, and only the first part needs the kernels that match before contexts against the converted text. The split is made on the rules as extracted, before the other passes: `DisambiguateOrder` restates single-character rules with negated after contexts (`[^末片]`), whose sets would join nearly all the components. Of the CLDR transforms, only Hans-Hant is split by default: its first part has 245 subgroups and 934 string rules (the rounds still chunked: 10 in the core), the second 14 subgroups (2,522 unconditional characters) and 24 string rules. On `nat-zh` (20 MB, 4 threads), 4.21 s unsplit, 3.81 s split, with identical output on the whole corpus and the same as ICU4C on its first 5,846 lines. `QA/xlit_split_components_test.py`.

**Status (2026-11-17): first increment implemented.** A correction kernel whose converted rules are all single-character subgroups with before contexts of fixed items (any number), and which has no insertion rules, resolves them by a While loop instead of rounds (`FusedRulesConfig::resolve`, `resolvableByWhile`; `--converted-context-while`, default on, `=0` for the rounds; kernel signature `W`). The string matches and the coverage of the subgroups do not depend on the converted text there, so they are settled as after the rounds, before the loop.

- **Outcomes.** Each position has a base outcome (the state given, the string rules and the other subgroups; slots compiled as in `matchConverted`), and each converted subgroup that may apply there (its positions without its before context) has its own, from static classes of its mappings: the characters whose replacements have length l, and whose slot i is in an item's set or not (`mappingLengthChars`, `mappingSlotChars`, added to `fusedClassSets`).
- **State**, per item (set, boundary) and distance j = 1 .. depth (`resolvedItems`), all accumulating: `YI`/`YO`, the j-th last converted character up to and including the position known in the set or known not; `K1`/`K0`, the same before the position, `MatchStar(Advance(Y) ∨ start ∨ K, KDel)`; `KDel`, the positions known deleted. A position of length l < j reads `K[j − l]`: the distance-2 streams come from the end of the character before, as planned.
- **The loop.** Each iteration evaluates the subgroups' contexts from `K1`/`K0` (`T` = ∨ alternatives ∧ items `K1`, `F` = ∧ alternatives ∨ items `K0`) and adds to the state the outcome of a subgroup known to apply, or of the base where all are known not to, or of any position whose possible outcomes all agree (consumers need no iteration). It ends when no `K1`/`K0` bit is added. Before the loop, the state of the positions where no converted subgroup may apply.

## 2. Staged sequential selection between rounds

Where string matches must be selected sequentially (cyclic or two-way overlaps, `TransformStep::sequentialSelection`) and the whole group is corrected, each round is a pipeline stage: a `FusedRules` kernel matching the before contexts against the previous round's converted text (`matchOnly`), a `LeftmostMatches` scalar scan, and a `FusedRules` kernel applying the rules where selected. That is 3 kernel calls per round, 27 at the defaults. The per-group kernel counts confirm it: each of these groups has exactly 21 more kernels at 8 rounds than at 1.

A single kernel with a While loop could fold all three: decided matches and contexts grow left to right, so the selection and the converted contexts resolve together. `LeftmostMatches` is exact and cheap on its own; the duplication, not the scan, is the cost.

## 4. Blocking depth in DeferredPlan

Inside every `DeferredPlan` kernel, the triggers whose before contexts may reach an unreplaced trigger are found by an unrolled closure:

```
blocked = blockedBy(triggers ∧ matched)
repeat DeferredBlockingDepth (8) times:
    blocked = blockedBy(triggers ∧ (matched ∨ blocked))
```

That is 9 `MatchStar` steps per kernel, in each of the 8 rounds: 72 copies per deferred group, 144 in Jpan-Latn. The closure is monotone and moves rightward, exactly the form DivCode §10 shows a While loop computes exactly (accumulate `blocked`, frontier = triggers newly blocked). A chain of more than 9 triggers is currently under-blocked, so a trigger can be treated as ready while a trigger before it is unreplaced. Possibly a single `MatchStar` through the reach and the trigger texts suffices; that needs checking against the tails' classes. Small change, exact, cheap: recommended first.

**Status: committed in 5a372fd94 (2026-11-17).** `DeferredPlan` now computes the closure with a While loop (`tools/ldml/xlit.cpp`, kernel renamed `DeferredPlanW_…` so that cached kernels are not reused; `DeferredBlockingDepth` removed):

```
Blocked  = blockedBy(triggers ∧ matched)
Sources  = triggers ∧ matched
Frontier = triggers ∧ Blocked ∧ ¬matched
while (Frontier) {
    Sources  = Sources ∨ Frontier
    Blocked  = Blocked ∨ blockedBy(Sources)
    Frontier = triggers ∧ Blocked ∧ ¬Sources
}
ready = triggers ∧ ¬Blocked
```

Every Var only gains bits and each iteration starts again from all the blocking triggers, the form DivCode §10 shows exact although the loop's carries from the previous block reach its first iteration only. The initial values are built on the streams, not on the Vars.

**The form of every new loop quantity** (DivCode §10, section 4): the carries of the previous block reach the first iteration only, so every value carried between iterations is a pair of accumulating Vars (known true, known false), each computed from positive seeds. For instance, known not covered by a run is a `MatchStar` from the positions that certainly end the run through the ends of candidates known not to apply, never `¬runTail(maybe applied)`. A carry-in lost in a later iteration then only leaves a value less complete, never wrong. The positions of the previous block are all decided at its end (before contexts and coverage look only left), so the first iteration's carries are exact.
